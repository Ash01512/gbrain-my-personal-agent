## Problem Statement

Job hunting in the UAE operations/asset-data market means repeating the same four
steps for every role: find the posting, judge whether it is actually a fit, rewrite
the CV framing and a cover letter for it, then remember what was sent where and when
to follow up. Steps one through three are slow and repetitive. Step four is the one
that silently fails — applications get lost, follow-ups never happen.

The database for step four already exists (`job-tracker` Supabase project, three
tables, shipped in PR #1). Nothing fills it. This design covers the agent that does.

## What Makes This Cool

The agent wakes up on its own, reads the market, and has a ranked, drafted queue
waiting before the day starts. The work that was an evening of tab-juggling becomes
a five-minute skim over coffee: read the score, read the draft, approve or bin.

The second-order effect is better: every application becomes structured data. Which
framings get replies. Which companies never respond. Which score band actually
converts. A job search normally leaves no evidence behind — this one accumulates it.

## Constraints

- **Indeed exposes no apply endpoint.** The connector has exactly four tools:
  `search_jobs`, `get_job_details`, `get_company_data`, `get_resume`. Both search
  tools instruct that results carry an apply link "so the user can click the job
  titles to apply." Submission is a human action by design.
- **Connectors are Claude-side, not code-side.** A Cloudflare Worker has no MCP
  client and no connector credentials. Anything that must read Indeed has to run
  inside a Claude session.
- **Supabase RLS is on with no policies.** Server-side access needs the service-role
  key, which is why the Worker requires its own shared token.
- One CV, one market, one person. No multi-tenant concerns.

## Premises

1. One blended track: operations / asset data in the UAE, AED 50k+ floor. Not two
   personas. The CV is positioned as "Operations & Asset Data | Predictive
   Maintenance | Facilities Engineering" — 12 years of facilities as the
   credibility, the MSc as the direction.
2. The CV carries two unfilled placeholders — the GitHub URL in the header and the
   entire `TECHNICAL PROJECTS` block. Nothing is sent to any employer until both are
   filled. This is a blocker, not a nice-to-have.
3. `job-tracker-worker` stays the API and dashboard. Supabase stays the state. The
   agent is a new component, not a rewrite.
4. The human presses submit. The agent never does.

## Approaches Considered

### Approach A: Claude Routine as the brain (CHOSEN)
Scheduled Claude session wakes daily, searches Indeed, scores against the CV, drafts
cover letters, POSTs into the Worker API. Worker serves the API and the approval
dashboard; Supabase holds state.
Effort: S-M. Risk: Low.

### Approach B: GitHub Actions + Anthropic API
Scheduled workflow calls the Claude API directly and writes to Supabase.
Rejected: loses the Indeed connector entirely, so job discovery — the input to the
whole pipeline — becomes the unsolved problem.

### Approach C: Cloudflare Cron Trigger on the Worker
Worker wakes itself and does the whole loop.
Rejected for the same reason as B, plus Worker CPU limits make long model calls
awkward.

## Recommended Approach

**Approach A.** It is the only design where the connectors that already exist are
reachable by the thing doing the work. It also adds the least: the Worker needs two
new endpoints and one migration, and everything else is already written and unit
tested. (Unit tested, not deployed — the Worker has never run against the live
Supabase project. See "Not yet verified" in `job-tracker-worker/README.md`.)

Division of labour:

| Component | Responsibility |
| --- | --- |
| Claude Routine (daily) | Search Indeed, score fit, draft cover letter, POST to Worker |
| Worker API | Validate, dedupe, persist, serve the queue |
| Supabase | State: applications, cv_versions, cover_letters |
| Dashboard | Skim, approve, reject, open the apply link |

Dedupe is free: `applications.job_url` already carries a unique index, and the Worker
already maps the resulting `23505` to a 409. A re-run cannot double-queue a role.

## Open Questions

1. **Scoring rubric.** What makes a role an 8 rather than a 5? Needs to be written
   down explicitly, or the score is unfalsifiable and you stop trusting it by week two.
2. **Volume.** How many queued roles per day is useful before the queue becomes
   another thing to ignore? Suggest capping the daily queue and tuning from there.
3. **Reply detection.** Gmail is connected, so the agent could move an application to
   `screening` when a recruiter replies. Valuable, but it is a second loop — worth
   deferring until the first one is proven.
4. **Cover letter voice.** Generated letters read as generated unless grounded in
   specifics from the CV. The Idiolect connector exists for exactly this and is worth
   evaluating once drafts are flowing.

## Success Criteria

- A day passes with no human involvement and the queue has scored, drafted entries.
- Approving an entry takes under a minute.
- A re-run queues zero duplicates.
- After four weeks, the tracker can answer: how many applied, what reply rate, which
  score band converts.

## Distribution Plan

Existing pipeline covers it. The Worker deploys with `wrangler deploy`; the repo is
public on GitHub. The Routine is configured in the user's Claude account and is not
itself distributable — the repo carries its prompt and setup instructions instead.

## Next Steps

1. **Fill the two CV placeholders.** Blocker. The `TECHNICAL PROJECTS` section is
   filled by this project — a Worker with Supabase, RLS, 66 tests, and a real
   security decision to explain end to end. Say "deployed" only once it is.
2. ~~**Migration**~~ DONE — `migrations/0000_init.sql` (baseline plus the
   `job_url` unique index the dedupe depends on), `0001_add_matching.sql`
   (`match_score`, `match_rationale`, `cv_version_id`, 0-10 check, indexes),
   and `0002_verify.sql` (changes nothing, raises if the live schema does not
   match — `create table if not exists` repairs no drift, so the baseline
   landing cleanly is not evidence that it matches).
   Queued roles reuse the `saved` status, so the CHECK constraint is unchanged.
   **Run all three in the Supabase SQL editor before first use**, and read the
   header of `0000` first: enabling RLS is a one-way change that makes the anon
   key read zero rows without returning an error.
3. ~~**Worker**~~ DONE — `POST /api/queue` (agent intake, scored candidate),
   `POST /api/applications/:id/apply` (records the send, returns the apply URL),
   `GET /api/stats/daily` (per-day counts). Named `apply`, not `approve`.
4. ~~**Dashboard**~~ DONE — queue sorted by fit with the rationale on hover, an
   Apply button that opens the posting and records it, and a daily counter.
5. **Routine:** daily prompt — search, score against the CV, draft, POST to
   `/api/queue`. Start manual, schedule once the output is worth reading.
   *This is the remaining piece.*
6. **Seed `cv_versions`** with the real CV so drafts have something to ground in.
7. **Set `APP_TIMEZONE`** to `Asia/Dubai` on the Worker, or the daily count rolls
   over at 04:00 local.

### Known gap

Every caller shares one `API_TOKEN`, so anything holding it can PATCH a
back-dated `applied_on` and move the daily count. Single-user trust model, not
an enforced boundary. A write-restricted agent token would close it.

### Reviewed 2026-08-19

Four review passes — code, security, design, developer experience — plus an
adversarial red team and a test-coverage audit. What changed:

- **Stored XSS through `job_url`** (P0). The agent ingests third-party job
  postings; a `javascript:` URL reached an `href` and a `window.open()` on the
  Worker's own origin, where it could read `API_TOKEN` out of `localStorage` —
  and that token fronts a service-role key that bypasses RLS. Now rejected on
  write and re-checked at both sinks.
- **`status` and `applied_on` are one fact.** An explicit `applied_on: null`
  used to slip past the stamp, and reverting a row to `saved` left the day it
  was recorded inflated forever. Both directions are enforced now.
- **Capped tallies are labelled.** `/api/stats` read 1000 rows unordered and
  reported the result as a total; both stats endpoints now return `truncated`
  and the dashboard renders `1000+`.
- **PostgREST grammar injection** through the search box: a company name with a
  comma broke the `or=` logic tree into a 400.
- **The dashboard was laid out as a CRUD tool.** The queue now leads, the match
  rationale is visible text rather than a hover tooltip, apply discloses what it
  does and offers an undo, and the seven-column table becomes cards on a phone.
- **The test suite never constructed a `Request`.** It does now: 125 tests, with
  the fetch handler, the apply state machine and the client-side helpers covered.
